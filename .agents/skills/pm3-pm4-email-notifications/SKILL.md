# PM3 → PM4 email notifications

PM3 email is not one asset. Inventory native task settings, `EmailEvent`, templates, Actions by Email, and every mail-sending trigger before selecting a PM4 destination. The converter uses static pattern matching only: it never executes or broadly translates PHP.

**Prerequisite:** [pm-analyze](../pm-analyze/SKILL.md) report on the same export. **Source:** [pm3-email-template](../pm3-email-template/SKILL.md) and [pm3-trigger](../pm3-trigger/SKILL.md). **Targets:** [pm4-send-email](../pm4-send-email/SKILL.md), [pm4-action-by-email](../pm4-action-by-email/SKILL.md). **Parent:** [pm3-pm4-migration](../pm3-pm4-migration/SKILL.md).

Ask if unclear: *“Plan only, or convert the safe email mappings after we review HITL rows?”*

```bash
PM="<skills-checkout>/skills/pm-analyze/pm-analyze"

"$PM" report-email-notifications \
  --pmx2 <export.pmx2> \
  --out email-notification-plan.json
```

Review every item and action before `convert`. Sanitized worked rows: [examples.md](examples.md). Sample output: [email-notification-plan.json](../../tools/pm-migrate/testdata/email-notification-plan.json).

## Destination rules

| PM3 source | PM4 destination |
|------------|-----------------|
| Event email in a before-routing trigger on task A | Task A `pm:config.email_notifications`, `sendAt: task-end` |
| Next-assignee helper | Each destination task B notification, `sendAt: task-start`, recipient `assignedUser` |
| Native `TAS_SEND_LAST_EMAIL=TRUE` | Destination task-start assigned-user notification |
| Safe native BPMN Email Event | Send Email `serviceTask` at the event position |
| Shared HTML wrapper | One EMAIL screen reused by notification entries |
| Real `ABECONFIGURATION` | `abe`; hand to [pm4-action-by-email](../pm4-action-by-email/SKILL.md) |
| Empty trigger case / unused or system ABE template | `exclude` |
| Unsafe or unresolved behavior | `hitl`; rebuild explicitly, often Script Task + Send Email |

`@@VAR` and simple `@#VAR` wrapper tokens become `{{VAR}}`. This does not preserve PM3 typing or escaping; verify rendered HTML. A PM3 group/user UID is instance-specific and must be resolved on the PM4 target.

## External subject/body table

If trigger helpers load content from an external table, the plan uses `external_template_table` and placeholder content. Supply a sanitized CSV or JSON only when the source values are available:

```bash
"$PM" convert \
  --pmx2 <export.pmx2> \
  --notification-table notifications.csv \
  --out process.json
```

Columns/keys: `task_uid` or `task_title`, `event`, `subject`, `body`. Do not commit customer content. Use `--skip emailnotif` to omit all generated email mappings while preserving the rest of conversion.

## HITL reason codes

Do not silently drop these:

`external_template_table`, `static_address_table`, `dedup_cc_list`, `parallel_wait`, `attachment_from_case_document`, `custom_email_server`, `from_override`, `missing_template_file`, `grid_token`, `unresolved_group`, `unmapped_system_variable`, `self_service_destination`, `final_task_no_next`.

For an item with both safe and unsafe actions, generate only the safe actions and keep the unsafe action visible in the plan. Script Task mail after parallel waits remains HITL; do not attach it to a human task with an empty XPath.

## Import contract

- Task config must be valid JSON at `pm:config.email_notifications.notifications`.
- Notification EMAIL screens require process dependents of type `notification_screen` with both `meta.path` and `meta.index`.
- Email Event Send Email screens use dependent type `screens` with `meta.path`.
- The same imported EMAIL screen may be referenced by many notification dependents.
- Actions by Email is reported, not generated by this converter path.

See [pm4-send-email notifications](../pm4-send-email/notifications.md) and [import-package-rules.md](../pm3-pm4-migration/import-package-rules.md).

## Verify

- [ ] Plan covers every mail trigger case/attachment, native setting, Email Event, template, and real ABE row
- [ ] Empty ABE rows and ABE system templates are excluded from user-template counts
- [ ] Every action has one destination and all HITL reason codes remain visible
- [ ] `task-end` stays on the source task; `task-start assignedUser` stays on the destination task
- [ ] Target users/groups and email servers are resolved rather than copied blindly
- [ ] Imported Modeler shows all notification entries and EMAIL screens
- [ ] Run one request for task-end, next-assignee, and conditional mail only when explicitly requested
- [ ] Real delivery is verified with an Email Server and queue worker; static package checks are not delivery proof
